Software Systems Research Report

Taskly

Architecture, data models, mobile interface, backend services, and implementation assessment
Project: Taskly — internal team task management
Study type: Static source-code and configuration review
Review date: 7 October 2026
Platforms targeted: Android and iOS

Prepared from the project files in the supplied repository. This report describes observed implementation and distinguishes it from backend scaffolding that is present but not connected to the current mobile data path.

Abstract

Taskly is a cross-platform Flutter application for assigning, tracking, and discussing team tasks. The codebase combines a presentation layer built from Flutter screens and reusable widgets, Riverpod state providers, a repository layer, and a Firestore-backed shared data store. It includes task creation and lifecycle actions, priorities and due dates, team and administrative views, a calendar, analytics, comments, subtasks, activity timelines, and push-notification support. A separate Supabase design is also supplied: PostgreSQL schema and row-level security (RLS), task-operation RPCs, retention and reminder functions, and two Deno edge functions.

This study maps the source tree and follows the main data paths. It finds a significant integration boundary: application repositories call Firebase Firestore, while Supabase is configured and documented as a second backend design but is not used by those repositories. The application therefore currently behaves as a Firebase-oriented implementation with a parallel Supabase target, rather than as a single integrated Firebase–Supabase system. The supplied app also contains a few demo-oriented authentication and persistence choices that should be replaced before production use. The report provides architecture and workflow diagrams, a catalogue of domain models and dependencies, a security and reliability assessment, and a staged implementation roadmap. No machine-learning model or AI inference component is declared in the codebase.

Keywords: Flutter, task management, Riverpod, Firebase Firestore, Supabase, PostgreSQL, row-level security, push notifications, mobile architecture.

1. Introduction and scope

Taskly addresses a familiar coordination problem: a team needs a shared place to define work, assign responsibility, follow progress, and surface due work. The project targets mobile devices, uses a single Flutter/Dart codebase, and provides role-aware task management concepts. Its screens cover both an individual contributor’s work and a small organization’s administration and reporting.

This report treats “model names” as the application’s domain/data models and enumerates them explicitly. It also records framework and service product names. A source search found no TensorFlow, PyTorch, Core ML, ONNX, or other trained/inference model implementation. Thus there is no AI/ML model name to report; the term model here refers to entities such as TaskItem and UserProfile.

The analysis is based on tracked source and configuration, not a running production environment. It does not infer that a cloud resource is deployed merely because a migration, function, credential filename, or dependency exists.

3. System architecture and runtime boundaries

The current mobile architecture is feature-oriented. Screens depend on Riverpod providers; providers call repository classes; the repositories mostly delegate to the singleton MockDataStore. Despite its name, that store is not purely mock: it subscribes to Firestore snapshots and performs Firestore writes. It also keeps an in-memory copy for synchronous filtering and immediate UI refresh.

Figure 1. As-built architecture inferred from imports and repository calls. Firebase carries the current client data path; Supabase assets describe a separate target implementation.
Integration status: supabase_flutter is declared and configuration/migrations/functions exist, but the inspected feature repositories call FirebaseFirestore.instance via MockDataStore. The app bootstrap initializes Firebase. This distinction matters for data ownership, security review, deployment, and any statement that the app is “Supabase-backed.”

4.2 UI system

Theme files centralize colors, typography, spacing, and light/dark themes. Shared components include task cards, priority badges, status chips, stat cards, avatars, bottom navigation, buttons, text fields, dropdowns, tabs, empty states, and completion sheets. google_fonts supplies typography; fl_chart and table_calendar support analytics and calendar visualization. The app constrains initial orientation to portrait while the iOS plist also advertises landscape orientations, so platform orientation behavior should be confirmed as an explicit product choice.

5. Application state and data flow

Riverpod supplies dependency access, computed providers, and mutable UI state. The task provider exposes all tasks, per-user task subsets, task details, activity and attachment projections, dashboard statistics, task search, and status filters. The notifier calls repository operations and increments a revision state so dependent providers recompute. Firestore snapshot listeners in the shared store replace in-memory lists and invoke a callback to refresh task state.

Figure 2. Typical state and data propagation for task operations.

Several mutations update the local list before the Firestore write completes. This makes the interface responsive but creates a need for rollback/error reporting and concurrency handling. Some write calls are not awaited; the code should avoid presenting success as durable until failure paths are handled.

5.1 Core policies and utilities

The shared utility layer contains email/password/title validation, attachment MIME and 20 MiB size checks, due-date bucketing (overdue, today, tomorrow, upcoming, or none), and a 350 ms debouncer. TaskPolicy expresses UI-level start/complete eligibility, priority/due-date ordering, and the todo → in-progress → completed transition. These client-side rules improve consistency but do not replace backend authorization. Local preferences persist the theme setting; date/time extensions and app exception types provide formatting and error vocabulary.

Cardinality difference: the mobile TaskItem supports a list of assignee IDs, but the Supabase tasks table has a single assigned_to UUID. The current Firestore representation and proposed relational schema therefore do not have identical task-assignment semantics. A migration needs either a join table (recommended for true multi-assignment) or an explicit product decision to restrict tasks to one assignee.

7. Backend and persistence systems

7.1 Firebase path currently called by the app

The Flutter startup initializes Firebase using generated platform options, and MockDataStore.initFirebaseSync listens to Firestore collections named users, tasks, activities, attachments, and notifications. Login reads users by email fields; task and member actions write documents directly. The login flow writes an FCM token under fcm_tokens. The store seeds a default organization and one in-memory profile, while live snapshots become the effective shared collection state.

7.2 Supabase schema and server-side design

The migration creates enums, organizations, profiles, settings, tasks, task activity, notifications, device tokens, task attachments, and task reminder-deduplication records. It adds foreign keys, check constraints, query indexes, and updated_at triggers. Helper functions derive the authenticated profile/organization/role, and admin checks distinguish founder and admin roles.

RPC operations include task creation, starting and completing tasks, admin member upsert, due/overdue reminder dispatch, and retention purge. The SQL path performs task state changes, activity logging, and notification insertion together, giving stronger transactional semantics than multiple independent client writes. RLS policies scope access to an organization and constrain profile, task, notification, token, attachment, and storage access. SQL policies should remain the authoritative authorization layer even if the UI hides disallowed actions.

Two Deno edge functions are included. send-push reads recipient device tokens with the service role and sends Firebase Cloud Messaging v1 messages using a service-account JWT. due-reminders invokes the reminder-dispatch and completed-task-purge RPCs and optionally checks a cron bearer secret. In supabase/config.toml, JWT verification is disabled for both functions; therefore the handler-level secret and deployment/network policy are especially important for due-reminders, and the push function needs an authenticated database webhook or equivalent request validation before deployment.

8. Authentication, authorization, and security

The live email sign-in implementation queries Firestore for a user record and compares a submitted password to a stored password field, with demo fallback behavior. It persists the email and password in SharedPreferences and reuses them to restore a session. Google sign-in currently selects a predefined profile after a delay; no Google OAuth exchange is implemented in the inspected repository. These are demo mechanics, not production-grade authentication. The Supabase migration’s use of auth.users, profile mapping, RLS helpers, and admin RPC checks represents a more appropriate target, but the Flutter app does not currently invoke that path.

9. Notifications, scheduling, and attachments

In-app notifications are created for assignment, task start/completion, comments, and selected updates. The app requests FCM permission and stores a device token. Native local notifications are initialized through Awesome Notifications, and the app registers an action listener. A separate Python process watches Firestore notifications whose push_sent field is false and sends FCM messages. This path coexists with the Supabase edge function that can send FCM through the v1 API. The runtime should choose one delivery authority and define token refresh, invalid-token cleanup, retry policy, idempotency, and payload routing.

Attachment dependencies support picking files/images, caching remote images, resolving paths, MIME detection, and opening files. Firestore task models include attachment name/base64/local path fields, while the Supabase relational design stores attachment metadata and imposes a 20 MiB limit plus Storage policies. Large binary payloads should live in object storage; database documents should carry metadata and a storage object key.

The Supabase reminder function operates in UTC by converting current time to a UTC date and compares reminder dates. The mobile date helpers use local DateTime fields. A production contract should make timezone ownership explicit (organization timezone or user timezone), including the meaning of “due today,” daylight-saving transitions, and the exact timestamp-to-date conversion.

11. Quality, limitations, and risks

Strengths

  • Clear feature folders separate authentication, tasks, team, notifications, admin, calendar, home, profile, and design-system surfaces.
  • Reusable visual components and centralized theme files support UI consistency.
  • Typed domain models and status/priority/role enums make app-level concepts discoverable.
  • Firestore snapshot subscriptions provide cross-client updates in the current path.
  • The Supabase schema shows thoughtful relational constraints, indexes, RLS, audit events, atomic RPCs, reminder de-duplication, and retention cleanup.

Limitations evidenced by the repository

  • Backend duality: live Firebase access and unused Supabase design create uncertainty about the system of record.
  • Authentication is demo-oriented, and current task mutation methods mostly do not enforce authorization in the client repository.
  • Direct Firestore writes split a logical operation such as task creation into separate task, activity, and notification writes; partial failure can leave inconsistent state.
  • The singleton store uses mutable in-memory lists, while snapshot listeners and writes can race; write errors are not consistently surfaced.
  • Some features appear richer in the SQL target than in current UI/runtime (for example relational attachment storage, retention RPC, and admin RPC).
  • The root README is a starter template, and test coverage visible in the tree is minimal; this report did not execute tests.
  • There are multiple notification mechanisms and overlapping notification packages, which increase lifecycle complexity.

For backend consolidation, the supplied Supabase design is a stronger starting point for tenant isolation and atomic task transitions, but adopting it requires implementing the Flutter Supabase auth/data path and migrating Firestore data. Keeping Firebase instead is also viable, but then Firestore security rules, transactions/batches, storage, scheduled jobs, and server-side authorization need to become the canonical documented design. Running both as independent writable sources should be avoided.

13. Conclusion

Taskly is a feature-rich mobile task management prototype with a coherent Flutter presentation layer and a broad set of task, team, and notification concepts. Its current runtime path is Firebase Firestore plus Riverpod-backed in-memory projections. The repository also contains a substantially developed Supabase relational target, including RLS and server-side workflows, but the code inspected does not connect the app repositories to that target. This difference is the central architectural finding.

The most important next steps are to choose one backend, replace demo authentication, align the data model contracts, and make task lifecycle writes atomic and observable. The project defines business data models but no AI/ML inference model. Once these boundaries are settled, the existing screens and shared components provide a useful base for a secure, testable production application.
